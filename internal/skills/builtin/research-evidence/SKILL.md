# research-evidence

Use this procedure only for an assignment whose deliverable needs it. Read the
actual role contract, owned paths, user constraints and current tool descriptions.
The role's preferred skill binding is a starting recipe, not additional access.

## Capability and input preflight

- Identify the exact source, reference, requested output and acceptance criteria.
- Inspect available native tools, permitted commands and connected MCP schemas.
- Check optional runtimes/renderers with scoped commands before depending on them.
- Preserve user references, repository conventions and unrelated working changes.
- Existing authentication and permission/hook controls apply to every action.
- Report missing capability precisely; continue independent authorized work.

## Domain procedure

1. Define the question, scope, decision and evidence that could change the recommendation. Avoid collecting unrelated material.

2. Inspect local source and user-provided evidence first. Use available web_search/fetch for unstable external claims with version/date attribution.

3. Prefer primary documentation, datasets and original research; distinguish marketing claims and third-party interpretation.

4. Record sources, retrieval date, relevant version, method and assumptions. Preserve the distinction between observed, inferred and unverified.

5. Compare options using consistent criteria, conditions and units. A missing measurement is not a zero value.

6. For experiments specify hypothesis, intervention, baseline, workload, sample size and excluded cases before interpreting outcomes.

7. Separate tool/runtime time from provider/model latency and retries; compare comparable configurations and report distributions when measured.

8. State causal limits and alternative explanations. Similar output or a single fast run is insufficient evidence for a general performance claim.

9. Use artifact templates for report structure only; do not invent facts, quotes or numerical results to complete sections.

10. Keep a bounded evidence ledger linking each consequential conclusion to its supporting source and contradictions.

11. Answer the decision with a concrete recommendation, tradeoffs and the smallest actions resolving decisive unknowns.

12. Deliver findings, source references, methodology, observed results and remaining uncertainty in the requested handoff format.

## Research question and source ledger

Write the decision or hypothesis the research should inform.
Define scope, version, platform, date relevance and exclusion criteria.
Search for primary sources that address that question directly rather than
collecting a large set of loosely related pages.

For each material source, retain identity, publication/update date where available,
applicable version and the claim it supports. Distinguish source statements,
your inference and measured observations. Record contradictions instead of
silently averaging incompatible claims.

A local cached skill describes a procedure and its environment. It does not prove
the underlying service or runtime is available in Atlas.

## Experiment design

State the hypothesis, manipulated factor, outcome, control conditions and
disconfirming observation. Match fixtures, environment and timing conditions
when comparing implementations.

Record repeated observations when variability matters; a single fast run is not
a stable performance guarantee. Separate provider waiting, tool execution and
recovery only when instrumentation can establish those intervals.

For analytical reports, define denominators, units and source population.
Exploratory results and confirmatory evidence must be labeled distinctly.

## Synthesis and freshness

Prefer directly relevant evidence over repeated secondary claims.
Check that product versions, interfaces and dates align before combining sources.
Do not use an older source as proof of a newer model or capability without
verification.

If authoritative sources disagree or access is unavailable, state the exact
uncertainty and how it affects the decision. Continue independent research instead
of inventing precision.

Example: compare two CLI workflows using the same model, prompt and reasoning
settings, record actual call counts and task outcomes, then distinguish measured
elapsed time from a proposed explanation of the difference.

Deliver source-backed conclusions, reproducible method, raw observation summary
and unresolved questions. Cite navigable sources and avoid unsupported rankings.

## Verification and recovery

Bind each important criterion to a real check and a navigable artifact or source.
Distinguish fresh executed results, cached results, structural checks, inspected
renders, skipped checks and user-reported observations. When a prerequisite fails,
stop dependent actions and retain the first failure, current identity and recovery
options. Retry within bounds only after identifying a relevant changed condition.
Do not repeat uncertain writes, suppress failures or fabricate missing evidence.

## Delivery

Return the assignment's requested output schema. For workflow tasks use the Atlas
JSON handoff with actual changed_files, checks, dependencies, risks and decision.
Include artifact paths and source provenance in evidence. A ready handoff is a
reported result for coordinator verification, never authenticated completion.
In quality-only runs do not implement fixes, change tests or certify unseen output.
