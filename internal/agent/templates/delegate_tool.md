Break a task into subtasks and run each one on a named agent, in parallel, then get every result back together.

This is the decomposition counterpart to `orchestrate`: `orchestrate` runs the SAME prompt on several agents to compare or verify their answers; `delegate` runs a DIFFERENT prompt on each one, because the subtasks are different pieces of work, not the same question asked twice. Use `delegate` when a task naturally splits into independent parts (e.g. "update the frontend form" and "update the backend validation" for one feature) that don't need to see each other's output to do their part. Use `agent` instead for a single task, and `orchestrate` when you want several independent takes on one question.

You decide the decomposition yourself -- this tool does not call a model to plan it for you, since you already have the full context of the task and are better placed to judge how it splits than a second opinion would be. Pass each subtask as one entry in tasks: agent_name (a configured subagent, from the list at the end of this description) and prompt (that subtask's own, self-contained instructions -- an agent only sees its own prompt, not the others' or the overall task description, so include whatever context that piece of work actually needs).

Requires at least two tasks -- for one task, call `agent` directly. Unlike orchestrate, the same agent_name may appear in more than one task (e.g. two different files for the same kind of change); that is not wasteful here, since each task carries different work. Results come back labelled by both the agent name and which task it was, in the order given.

Assignment contract: Each prompt must include its goal, relevant project context, precise owned files or read-only scope, constraints and authorization boundaries, dependencies, observable acceptance criteria, and required evidence. Assign disjoint write ownership before running tasks concurrently. Reviewers and researchers remain read-only unless explicitly assigned implementation. Shared interfaces and sequential dependencies belong to the coordinator until their contracts are settled.

Require each result to identify completed work, changed files or evidence locations, checks actually executed and their results, assumptions, and unresolved blockers or integration actions. Results are reports to inspect, not proof that the whole feature works. After this tool returns, inspect all results, resolve inconsistencies, integrate affected boundaries, run appropriate integration checks, and reconcile the full requirement ledger before claiming completion. Respect configured tool availability and budget; parallelism is useful when work is independent, not automatically free.
