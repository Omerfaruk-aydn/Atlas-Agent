Run known multi-step work as one bounded, verified program instead of one model turn per call. This is the default way to execute work whose targets are already observed. Use single computer/browser calls to discover targets, to handle something unexpected, or when the next step needs a new decision.

Plan in three moves: (1) load the tools you need and observe fresh targets (window_id, element_id, tab); (2) turn everything that is now known into one workflow with a checkpoint after every result that matters, including results in other windows or tabs; (3) end the workflow where unknown content appears (a dialog you have not seen, a search result to choose, a question, a permission, an uncertain mutation), observe it, then send the next workflow. Do not split known work into separate turns, one input per turn or a screenshot per input. Length is not a goal: correct dependencies and verification are. Stop at a boundary that needs a new decision; never invent an identity the plan cannot bind from a fresh observation or an earlier step.

Exactly one shape per call. Each is a JSON object, never a string containing JSON:
- `desktop`: desktop recipes. `mode:"flow"` is the long form: up to {%.FlowNodes%} nodes, forward edges only, all validated before the first input. Other modes: `"prepare"`, `"observe"`, `"act"`, `"fill_submit"`, `"sequence"`, `"adaptive"`, `"transition"`, `"rename"`.
- `browser`: `{tab_id, origin, steps:[...]}` with 1-{%.BrowserSteps%} semantic browser steps and optional `verify` assertions.
- `flow`: a reusable browser template run over 1-{%.FlowItems%} input items, with rerun of failed/uncertain items.
- `steps`: generic tool calls (1-{%.Steps%}) with `bindings`, `when`, `if_success`, `if_failed`, `require_passed`, `items` and `items_from`, plus pure `transform` steps that filter, extract, count or reshape earlier results without another model turn (help topic `steps`).
- `help`: one topic name; returns detailed rules and executable examples and runs nothing. Topics: {%.Topics%}.

Desktop flow nodes (window IDs are never written; nodes bind them at run time):
- `prepare` {application}: find, launch once if absent, focus and bind. `resolve` {application and/or exact title, owner_ref for a dialog}: bind an open window, waiting up to wait_ms.
- `operation` {window_ref, input or 1-{%.Inputs%} inputs, checkpoint, focus}: the inputs run once, then the checkpoint must pass. `checkpoint_ref` reads the checkpoint in another bound window; `closes_window:true` (e.g. file name + Enter in a Save dialog) proves the dialog is gone and checkpoint_ref is foreground again before reading. A checkpoint in another window never proves the input already took effect in its own window: a `set_value` is skipped as already applied only when its checkpoint reads the same live window and control.
- `verify` {window_ref, checkpoint}: read-only check. `branch` {checkpoint, then, else}: native predicate.
- `capture` {name, pattern, number} on an operation/verify node names its checkpoint readback; later nodes use `{{name}}` only in text, `expected` and `file.expected` fields, never in selectors, keys or paths. A verify node may omit `expected` to read the current value (the pattern is the check). Each placeholder must be captured on every path before use; a mismatch stops the flow before later input. Captures survive a durable resume.
- `file_check` {file:{path, condition: exists|absent|content|sha256, expected}}: read-only file-system check of a saved result.
- `rename` {window_ref, rename:{old_name, new_name, expected_full_name, on_conflict}}: verified Explorer rename; `expected_full_name` (e.g. "sonuc.txt" while Explorer shows "sonuc") is read from the window's shell item, never inferred from the label. If new_name exists: `on_conflict` `fail` (default, refuses with both files' sha256), `keep_both` ("sonuc (2)"), `use_existing_if_identical` (no input when bytes match). Nothing is ever deleted or overwritten.
- `close` {window_ref}: focus, Alt+F4 once, prove absence. It refuses windows that existed before the task (not_task_owned) unless `allow_unowned:true` because the user asked to close that window. A closed binding cannot be used again.
Checkpoints are native assertions with a selector (element_id, name, role) and condition: visible, hidden, enabled, text (UIA name), value, document_text, keyboard_focused, file_name. They need no screenshot; request an image only when pixels decide.

Results: every step or node reports its state. Flow `nodes` states are bound, evaluated, verified, uncertain, failed, blocked, canceled, not_run and skipped_branch; generic steps report status and outcome (only `verified` is a checked result). A failure stops dependent work; `resume` says what already took effect and where to continue. A node stopped by a permission, question, hook or cancellation before any of its inputs was sent reports `dispatch:"none"` (blocked, canceled or failed) and runs again on resume once allowed; a node whose input may have been sent is uncertain, is reconciled from fresh evidence and is never replayed automatically. Resume (`run_id` with `resume:true`) continues from the durable journal and re-resolves every window instead of trusting old handles. A halted child's question, permission or hook metadata is kept beside the flow ledger. A successful workflow proves its checkpoints, not the whole task: check every requested requirement (for a file: folder, full name and content separately) before reporting completion, and name what could not be verified.

Every child call uses the normal tool schema, hooks, permissions, focus/foreground guards, input settle and the desktop lease; denials, questions and cancellation stop the program. Limits: steps {%.Steps%} and {%.Invocations%} invocations; `timeout_ms` {%.MinTimeoutMS%}-{%.MaxTimeoutMS%} (default {%.DefaultTimeoutMS%}) bounds steps/browser/flow and a desktop flow (desktop flow default {%.FlowDefaultMS%}); desktop flow {%.FlowNodes%} nodes, {%.FlowCalls%} child calls; sequence {%.SequenceSteps%} steps in {%.SequenceSeconds%} s; act/prepare {%.RecipeSeconds%} s; {%.Inputs%} inputs per operation; {%.ContentKiB%} KiB content per step and {%.OutputKiB%} KiB output (details shorten first; ids, states and dispatch are kept). This is a JSON tool program, never code execution.
